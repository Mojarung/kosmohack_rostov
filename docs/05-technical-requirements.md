# Технические требования, воспроизводимость и состав решения

> Источник: «Космохакатон — Постановка задачи» ([PDF](source/postanovka-zadachi.pdf)), стр. 15–19.

Эксперты должны иметь возможность **воспроизвести финальный результат по предоставленному репозиторию и инструкции без ручного исправления исходного кода**.

## Запуск решения / инференс

Решение должно иметь **две воспроизводимые точки запуска**:

| Точка запуска | Что делает |
|---|---|
| **Веб-сервис** | Пользователь указывает регион и выбирает или рисует полигон, после чего данные собираются и анализируются автоматически |
| **Batch-инференс** | Технический режим: принимает `private_features.csv` и формирует `submission.csv` для строк `is_synthetic_gap = True` |

В веб-интерфейсе эксперт должен видеть:

- выбранный полигон;
- исходный и восстановленный ряд `primary_ndvi`;
- найденные негативные аномальные периоды и их интерпретацию.

Отдельный submission по статусам аномалий **не требуется**.

Допускается **любой стек**. В README должны быть указаны команды запуска веб-сервиса и batch-инференса, зависимости, настройки внешних API и ожидаемые входные/выходные файлы.

## Воспроизводимость

Воспроизводимость охватывает reference train, обучение/настройку алгоритмов, технический инференс и автоматический сбор данных веб-сервисом. Необходимо зафиксировать:

- внешние датасеты, геопорталы, API и идентификаторы используемых коллекций;
- логику поиска региона, выбора готовых контуров и задания произвольного полигона;
- маскирование облаков, агрегацию по полигону, расчёт индексов и формирование временного ряда;
- команды обучения и инференса, random seed и ключевые гиперпараметры;
- версии зависимостей, подготовку окружения и настройки доступа к внешним API;
- порядок запуска веб-сервиса и получения `submission.csv` в техническом режиме.

**Предпочтительно** предоставить Dockerfile / docker-compose или другой способ фиксации окружения; иначе README должен содержать однозначную инструкцию установки и запуска всех обязательных компонентов.

## Состав итогового решения

Для финальной технической проверки и экспертной оценки команда должна предоставить полный комплект материалов, позволяющий воспроизвести результат и понять проведённое исследование.

### Репозиторий

Репозиторий должен содержать полный исходный код решения:

- подготовку/загрузку данных (в той части, где это возможно);
- предобработку;
- обучение;
- инференс;
- модуль детекции аномалий;
- конфигурации.

Структура проекта должна быть понятной: точки входа, конфигурации и основные модули не должны требовать поиска по разрозненным файлам или ручного переноса кода.

### README.md

README должен позволять эксперту запустить решение **без обращения к команде**. Минимально необходимо описать:

1. назначение решения и структуру репозитория;
2. подготовку окружения и установку зависимостей;
3. источники и структуру данных;
4. команды/скрипты сбора и предобработки данных, если они предоставляются;
5. команду обучения или порядок подключения готовых артефактов;
6. команду инференса и место появления `submission.csv`;
7. способ запуска детекции аномалий и демонстрационного интерфейса.

### Окружение и зависимости

Команда должна зафиксировать версии зависимостей одним из стандартных способов:

- `requirements.txt`;
- `pyproject.toml` + lock-файл;
- `environment.yml`;
- `Dockerfile`;
- аналогичный механизм для выбранного стека.

Все внешние **системные** зависимости также должны быть перечислены.

### Модель, веса и другие артефакты

Если решение использует обученные модели, веса, скейлеры, сохранённые статистики климатологии, индексы, конфигурации или другие артефакты, они должны быть доступны организаторам и подключаться по инструкции без ручных доработок.

Допускается хранение больших файлов по внешней ссылке, указанной в README.

### Исследовательский отчёт

Помимо кода команда предоставляет **исследовательский отчёт в свободной форме**. Его задача — показать ход работы, обоснованность принятых решений и возможность воспроизвести результат.

Рекомендуется отразить:

- краткое описание задачи и протокола оценки;
- EDA: структура временных рядов, пропуски, сезонность, выбросы, различия между полигонами/регионами и другие значимые наблюдения;
- какие исходные и дополнительные данные использовались, откуда они были получены и почему были выбраны;
- baseline / отправную точку и её ограничения;
- проверенные гипотезы, эксперименты и сравнение вариантов решения;
- какие изменения дали или не дали прирост качества интерполяции;
- логику детекции аномалий, примеры найденных случаев и способ их интерпретации;
- обоснование финальной конфигурации решения;
- ограничения подхода, проблемные случаи и возможные направления дальнейшего развития;
- инструкции и параметры, необходимые для воспроизводимости обучения и инференса.

> Простая демонстрация графиков без выводов **не считается полноценным анализом**: важно показывать связку «наблюдение → решение/гипотеза → эксперимент → вывод».

### Презентация

Финальная презентация должна кратко показать проблематику, данные, выбранный подход и работающий результат. Рекомендуется включить:

- baseline и улучшение относительно него;
- итоговый GapScore / RMSE;
- логику детекции аномалий;
- 2–3 показательных временных ряда;
- архитектуру / пайплайн;
- демонстрацию интерфейса;
- выводы по ограничениям и развитию решения.

Во время защиты команда должна быть готова объяснить:

- происхождение обучающих данных;
- причины выбора методов;
- результаты ключевых экспериментов;
- как решение ведёт себя на новых полигонах/регионах.
